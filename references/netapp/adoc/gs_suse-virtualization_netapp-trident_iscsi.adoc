== Introduction

// = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = =

{svirt-brand} is a cloud-native virtualization platform that unifies virtual machine (VM) and container management, streamlining operations, and boosting efficiency with a single, cohesive platform for hybrid cloud infrastructure.
{ontap-brand} delivers unified data management, allowing you to manage, protect, and move data across your hybrid environment.
By leveraging {trident-brand}, you can deliver high-performance storage for virtual machines (VMs) hosted in your {svirt-brand} environment.


=== Scope

This guide covers the detailed steps required for setting up a three-node {svirt-long} cluster to consume {ontap-provider} storage.
It includes the {ontap} prerequisites, multipath configuration, {trident} installation, StorageClass definition, and basic validation.


=== Audience

This guide is intended for IT professionals responsible for virtualization and infrastructure management, such as infrastructure architects, systems administrators, or platform engineers.

To successfully follow this guide, you should have:

* Familiarity with {svirt-long} deployment and configuration
* Experience with {ontap-provider} storage provisioning and management
* Understanding of iSCSI concepts and configuration
* Working knowledge of Kubernetes

== Architecture

// = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = =
// Architecture
// = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = = =

The diagram below illustrates the basic architecture for {svirt-long} integrated with {ontap-long} storage.

image::architecture_diagram.png[title="Architecture: {svirt-long} with {ontap-long} and {trident}", scaledwidth="90%", align="center"]

The key components of the solution are:

* *{svirt-long}* is the cloud native solution that provides unified and streamlined orchestration for VMs and containers.
Built on Kubernetes, {svirt} delivers a flexible, scalable, and resilient infrastructure platform for all of your workloads.

* *{ontap-long}* data management software powers {ontap} storage systems.
With a global namespace that supports up to 24 hardware nodes of all types, {ontap} software supports unified storage (block and file), enabling significant workload consolidation that you can manage using the {ontap} System Manager GUI.
In this solution, {ontap} is used to provision iSCSI LUNs on the {ontap} storage back-end.

* *{trident-long}* is a Container Storage Interface (CSI) that delivers dynamic storage orchestration and natively integrates with Kubernetes.
{trident} enables consumption and management of storage resources across all popular {trident-provider} storage platforms, in the public cloud or on-premises.
{trident} runs as a single controller pod and a node pod on each worker node in the cluster.


When deployed together in the illustrated configuration, {svirt} nodes connect over the iSCSI protocol to {ontap-long} storage using the {trident} CSI.
High availability storage access is available when the cluster environment is configured with multipath support.

Guidance for deploying each layer of the solution are provided in the following sections.

=== Configuring iSCSI

Use CloudInit to create a persistent configuration of the iSCSI initiator.

. Define the configuration of the iSCSI initiator.

.. Create a CloudInit resource file for each cluster node, as shown below for the first node (`harvester-node-1`).
+
Each node needs its own CloudInit resource with a unique `metadata.name` and `spec.filename`, and with the host name, interface names, and IP addresses of that node.
{svirt} rejects a CloudInit resource whose `spec.filename` is already used by another CloudInit resource.
+
[source, yaml]
----
apiVersion: node.harvesterhci.io/v1beta1
kind: CloudInit
metadata:
  name: iscsi-ip-node1 <1>
spec:
  matchSelector:
    kubernetes.io/hostname: harvester-node-1 <2>
  filename: 01_iscsi_ip_node1.yaml <3>
  contents: |
    stages:
      initramfs:
        - name: "Configure iSCSI network interfaces"
          files:
            - path: /etc/NetworkManager/system-connections/iscsi-path1.nmconnection
              owner: 0
              group: 0
              permissions: 0600
              content: |
                [connection]
                id=iscsi-path1
                type=ethernet
                interface-name=eno3np0
                autoconnect=true
                [ipv4]
                method=manual
                addresses=192.168.100.87/24 <4>
                never-default=true
            - path: /etc/NetworkManager/system-connections/iscsi-path2.nmconnection
              owner: 0
              group: 0
              permissions: 0600
              content: |
                [connection]
                id=iscsi-path2
                type=ethernet
                interface-name=eno4np1
                autoconnect=true
                [ipv4]
                method=manual
                addresses=192.168.200.87/24 <5>
                never-default=true
----
+
<1> Set a distinct metadata name.
<2> Use the node's actual host name.
<3> Use a distinct file name.
<4> Set the correct IP address for the first path.
<5> Set the correct IP address for the second path.


.. Apply the CloudInit resource of each node. +
For example, apply the CloudInit resource to the first node with:
+
[source, console]
----
kubectl apply -f 01_iscsi_ip_node1.yaml
----

.. Verify that the CloudInit resources are created.
+
[source, console]
----
kubectl get cloudinit
----
+
[listing]
----
NAME              AGE
iscsi-ip-node1    20s

----

. Enable the iSCSI service daemon.

.. Create the `99_iscsid.yaml` CloudInit resource file. +
{trident} requires `node.session.scan = manual` in `/etc/iscsi/iscsid.conf`, so the CloudInit resource also sets this value.
With manual scanning, logging in to an iSCSI target does not add its LUNs to the node; {trident} scans the LUNs that it maps.
+
[source, yaml]
----
apiVersion: node.harvesterhci.io/v1beta1
kind: CloudInit
metadata:
  name: iscsid-start
spec:
  matchSelector: {}
  filename: 99_iscsid.yaml
  contents: |
    stages:
      network:
        - name: "Set manual iSCSI session scanning"
          commands:
            - sed -i 's/^node.session.scan = .*/node.session.scan = manual/' /etc/iscsi/iscsid.conf
        - name: "Enable and start iscsid"
          systemctl:
            enable:
              - iscsid
            start:
              - iscsid
----


.. Apply the configuration.
+
[source, console]
----
kubectl apply -f 99_iscsid.yaml
----

=== Enabling Multipath

. Create a CloudInit resource to auto-start the multipath daemon (`multipathd`) as shown below.
+
[source, yaml]
----
apiVersion: node.harvesterhci.io/v1beta1
kind: CloudInit
metadata:
  name: multipathd-config
spec:
  matchSelector: {}
  filename: 99_multipathd.yaml
  contents: |
    stages:
      network:
        - name: "Configure multipath.conf"
          files:
            - path: /etc/multipath.conf
              permissions: 0644
              owner: 0
              group: 0
              content: |
                defaults {
                    find_multipaths no
                    user_friendly_names yes
                }
                blacklist {
                    device {
                        vendor ".*"
                        product ".*"
                    }
                }
                blacklist_exceptions {
                    device {
                        vendor "NETAPP"
                        product "LUN"
                    }
                }
        - name: "Enable and start multipathd"
          systemctl:
            enable:
              - multipathd
            start:
              - multipathd
----

. Apply the configuration.
+
[source, console]
----
kubectl apply -f 99_multipathd.yaml
----


. Reboot the nodes one at a time.
+
{svirt} writes each CloudInit resource to the `/oem` directory of the matching nodes, and the node applies it at the next boot.
Wait until a node is back in the `Ready` state before you reboot the next node.

=== Deploying the {trident} CSI

. Prepare the worker nodes.
+
Before installing {trident-long}, ensure that each {svirt-long} node meets the prerequisites for Kubernetes storage integration.
Follow the official {trident-provider} documentation for {trident-docs-worker-prep}[Worker Node Preparation for {trident} CSI].

. Install {trident-long}.
//
+
The preferred installation method uses `tridentctl`, which is demonstrated in the following steps.
Be sure to check the {trident-docs-install}[{trident-provider} {trident} Installation Guide] for the latest details about obtaining and using `tridentctl`.

.. Download the `trident-installer` package. +
You can obtain the installer package from the Assets section on the {trident-installer-repo}[{trident-long} GitHub repository].
Copy the package's URL and download it on the command line with `wget`. +
For example:
+
[source, console, subs="attributes+"]
----
wget {trident-installer-url}
----
+
Be sure to use the URL for the version you wish to install.

.. Extract the `trident-installer` and associated files. +
For example:
+
[source, console, subs="attributes+"]
----
tar -xzf {trident-installer-file}
----

.. Change to the extracted directory.
+
[source, console, subs="attributes+"]
----
cd trident-installer
----

.. Initiate the installation.
+
[source, console, subs="attributes+"]
----
./tridentctl install -n trident
----

.. Verify that all {trident} pods are in the `Running` state.
+
[source, console]
----
kubectl get pods -n trident
----
+
[listing]
----

trident-node-linux-7qmcw                  2/2     Running   0          2m37s

. Configure the {trident} back-end.

.. Create a Kubernetes secret for your {ontap-long} storage controller credentials.
The `trident` namespace is created by the installation, so create the secret after installing {trident}.
+
[source, console]
----
kubectl create secret generic ontap-secret -n trident \
  --from-literal=username=admin \
  --from-literal=password='YourPassword'
----

.. Create a back-end configuration file, `ontap-backend.json` as below.
The `credentials` field references the secret, so the password is not stored in the file.
+
[source, json]
----
{
  "version": 1,
  "storageDriverName": "ontap-san",
  "managementLIF": "10.10.10.50",
  "svm": "harvester_svm",
  "credentials": {"name": "ontap-secret", "type": "secret"}
}
----
+
[NOTE]
====
Do not set `dataLIF` or `igroupName`.
{trident} discovers the iSCSI LIFs of the SVM, so each LUN gets a path through every iSCSI network, and it creates one initiator group per node.
{trident} ignores both fields for SAN back-ends and logs a warning.
====

.. Apply the back-end.
+
[source, console]
----
./tridentctl create backend -f ontap-backend.json -n trident
----

.. Validate the back-end.
+
[source, console]
----
./tridentctl get backend -n trident
----
+
[listing]
----

| NAME           | STORAGE DRIVER | UUID     | STATE  | USER-STATE | VOLUMES |
+----------------+----------------+----------+--------+------------+---------+
| ontapsan_XXXXX | ontap-san      | xxxxxxxx | online | normal     |       0 |

----


=== Defining the NetApp StorageClass and SnapshotClass

. Create the NetApp StorageClass.

.. Create a file, named `netapp-storageclass.yaml`, as shown below.
+
[source, yaml]
----
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: netapp-storageclass
provisioner: csi.trident.netapp.io
parameters:
  fsType: ext4
  backendType: "ontap-san"
reclaimPolicy: Delete
volumeBindingMode: Immediate
allowVolumeExpansion: true
----

.. Apply the StorageClass.
+
[source, console]
----
kubectl apply -f netapp-storageclass.yaml
----

.. Verify that the StorageClass is available.
+
[source, console]
----
kubectl get storageclass
----
+
[listing]
----
NAME            PROVISIONER            VOLUMEBINDINGMODE ALLOWVOLUMEEXPANSION
netapp-storageclass  csi.trident.netapp.io  Immediate         true
----


. Create the NetApp SnapshotClass.

.. Create a file, named `netapp-snapshotclass.yaml`, with the content below.
+
[source, yaml]
----
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: netapp-snapclass
driver: csi.trident.netapp.io
deletionPolicy: Delete
----

.. Apply the SnapshotClass.
+
[source, console]
----
kubectl apply -f netapp-snapshotclass.yaml
----

.. Verify the that the SnapshotClass is deployed.
+
[source, console]
----
kubectl get volumesnapshotclass
----
+
[listing]
----
NAME               DRIVER                  DELETIONPOLICY   AGE
netapp-snapclass   csi.trident.netapp.io   Delete           6s
----


=== Registering the {trident-provider} CSI driver in {svirt-long}

. Log in to the {svirt-long} UI.

. Go to __Advanced__ > __Settings__ > __csi-driver-config__.

. Click __Edit Setting__.

. Set the provisioner to `csi.trident.netapp.io`.

. Set the __Volume Snapshot Class Name__ to `netapp-snapclass`.
+
{svirt} uses this VolumeSnapshotClass for VM and volume snapshots on `netapp-storageclass`.
Without it, VM snapshots are rejected.

. Click __Save__.
+
[NOTE]
====
A VM backup to the {svirt} backup target also requires the __Backup Volume Snapshot Class Name__.
For volumes on `netapp-storageclass`, the backup target stores only the VM metadata.
The volume data stays on {ontap} as volume snapshots, so plan the protection of that data on the {ontap} side.
====

. Configure the {trident-provider} CSI driver as the default StorageClass.
+
{svirt} accepts only one default StorageClass, so unset Longhorn first.

.. Unset Longhorn as the default StorageClass.
+
[source, console]
----
kubectl patch storageclass harvester-longhorn \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"false"}}}'
----

.. Set the {trident-provider} CSI driver as the default StorageClass.
+
[source, console]
----
kubectl patch storageclass netapp-storageclass \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
----

Verify that you can create a virtual machine configured with the {trident-provider} StorageClass and which is backed by {ontap-long} iSCSI storage.


=== Creating an ISO image on {ontap} storage

The CD-ROM volume of a VM is created from the image.
If the image is stored in Longhorn, which is the default image back-end, a CD-ROM volume on `netapp-storageclass` is created empty and the VM cannot boot from it.
Create the image with the `cdi` back-end on `netapp-storageclass`, so that it is stored on {ontap} and the CD-ROM volume is cloned from it.

. Create a file, named `iso-image.yaml`, as shown below.
+
[source, yaml]
----
apiVersion: harvesterhci.io/v1beta1
kind: VirtualMachineImage
metadata:
  name: <image-name>
  namespace: <namespace>
spec:
  displayName: <image-name>
  sourceType: download
  url: <ISO-URL>
  backend: cdi
  targetStorageClassName: netapp-storageclass
----

. Apply the image.
+
[source, console]
----
kubectl apply -f iso-image.yaml
----

. Wait until the image shows a progress of `100`.
+
[source, console]
----
kubectl get virtualmachineimage <image-name> -n <namespace>
----


=== Creating a VM

. Log in to the {svirt} UI.

. Navigate to __Virtual Machines__ and click __Create__.

. Select a namespace for your VM.
+
[NOTE]
====
Only the `harvester-public` namespace is visible to all users by default.
====

. Provide a name for your VM.

. (Optional) Select a VM template (for example, `iso-image`, `raw-image`, `windows-iso-image`) to speed up provisioning.

. On the __Basics__ tab, configure the following settings:
+
--
* __CPU__: 2
* __Memory__: 4 GB
* __SSHKey__: Select an existing key or upload a new one (required if you need SSH access).
* (Optional) __Overcommit configuration__: Set CPU, memory, and storage overcommit ratios to allow scheduling of additional VMs even when physical resources are fully used.
* (Optional) __Other advanced settings__: Run strategy, OS type, or custom cloud-init data.
--

. On the __Volumes__ tab, select or add disks.
+
[NOTE]
====
One writable root disk is created by default.
====

.. Click __Add Disk__ and select `cd-rom` as the disk type.

.. Select the ISO image that you created on `netapp-storageclass` and set its boot order to `1`.

.. Choose the StorageClass named `netapp-storageclass`, which is provisioned by {trident}.

.. For the root disk, select the `netapp-storageclass` StorageClass and specify the desired size.


. The management network is added by default.
//
+
You can remove it if using VLAN networks.
Optionally, you can add additional interfaces (`VLAN`, `bridge`, `masquerade`).

. Review all settings and click __Create__ to deploy the VM.

== Frequently Asked Questions (FAQ)

. *What is the role of {trident} CSI in the {svirt} environment?*
+
--
{trident-long} acts as a Container Storage Interface (CSI) driver that integrates {ontap-provider} storage with Kubernetes-based platforms such as {svirt-long}.

It enables dynamic provisioning of persistent storage volumes for virtual machines and containers using {ontap-long} storage systems.
--

. *Why is multipath configuration required for {ontap-provider} iSCSI storage?*
+
--
Multipath provides high availability and redundancy for storage connections.

When multiple network paths exist between {svirt} nodes and the {ontap-provider} storage system, multipath ensures that:

* Storage traffic can fail over automatically if a path becomes unavailable.
* Performance is improved through path load balancing.
* Storage access remains uninterrupted during network or interface failures.
--

. *Why must the `netapp-storageclass` be configured as the default StorageClass?*
+
--
Setting `netapp-storageclass` as the default ensures that newly created volumes automatically use {ontap-provider}-backed storage unless another StorageClass is explicitly selected.

This simplifies VM provisioning and guarantees that persistent volumes are dynamically created through {trident} using the {ontap-long} back-end.
--

. *Can you expand a volume on `netapp-storageclass` while the VM is running?*
+
--
No. {svirt} rejects the expansion of a volume on `netapp-storageclass` while the VM is running.
Stop the VM, expand the volume, and start the VM again.
--

. *Can you deploy the {trident} CSI using methods other than `tridentctl`?*
+
--
Yes. While using `tridentctl` is the recommended installation method, {trident} can also be deployed using Helm charts.

Helm-based deployment is useful when you manage Kubernetes applications through a package management workflow.
--

. *Can {svirt-long} run both virtual machines and container workloads?*
+
--
Yes. {svirt} supports running virtual machines and Kubernetes workloads on the same infrastructure.

This unified platform simplifies operations and allows organizations to modernize applications while maintaining existing VM-based workloads.
--
